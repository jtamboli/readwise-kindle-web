Readwise Kindle Web Reader

A FastAPI-based web application that fetches articles from Readwise Reader API and displays them in a paginated, Kindle-friendly format.

Features

Kindle-optimized display: Minimal CSS, no JavaScript, optimized for e-ink displays. The design prioritizes readability on e-ink screens by avoiding complex layouts and animations that can cause ghosting or slow rendering on e-paper displays.

Smart pagination: Preserves block integrity while fitting content to Kindle screen. The pagination algorithm ensures that entire block-level elements like paragraphs, headings, and lists are kept together, preventing awkward mid-paragraph breaks that would disrupt the reading flow.

Reading progress tracking: Automatically updates your progress in Readwise. As you navigate through pages, the application silently updates your reading position in the background, allowing you to seamlessly switch between devices without losing your place.

Two-tier caching: Fast page loads with intelligent cache management. The caching strategy balances freshness of the inbox list with the performance benefits of caching full article content, ensuring quick page turns while keeping your reading queue up-to-date.

Archive support: Mark articles as read directly from the Kindle. When you finish an article, a simple tap on the Archive link removes it from your queue and marks it as read in your Readwise account.

Project Structure

The application follows a clean modular structure. The app directory contains all the core functionality: the main FastAPI application and routes, configuration management that handles environment variables, an async Readwise API client for efficient network operations, an HTML pagination engine that chunks content intelligently, and HTML sanitization to ensure only safe, Kindle-compatible markup is rendered.

Templates are kept in a dedicated directory, with separate views for the inbox list and individual article pages. The list view provides a quick overview of available reading material, while the page view focuses on delivering a distraction-free reading experience.

Setup and Configuration

Getting started requires creating a virtual environment and installing the necessary Python dependencies. The application uses modern async Python with FastAPI, providing excellent performance and a clean development experience.

Configuration is handled entirely through environment variables, making it easy to deploy in various environments. The most critical setting is your Readwise API token, which you can obtain from the Readwise website. This token allows the application to fetch your reading queue and update reading progress.

The page character budget is a key tuning parameter. The default of 1800 characters works well for most Kindles, but you may want to adjust it based on your specific device. Kindle Paperwhite users typically prefer 1500-1800 characters per page, while Kindle Oasis owners with larger screens can comfortably read 1800-2000 characters. Older Kindle models may benefit from a lower budget of 1200-1500 characters.

Image handling is configurable as well. By default, images are placed on separate pages to prevent layout issues and ensure images display at a comfortable size. This prevents the common problem of images being squeezed into a page with text, making both harder to read.

Design Philosophy

The design simplifies things considerably by targeting a fixed device type. With a known target platform, you can empirically determine your page budget once and hardcode it, eliminating the need for complex responsive design or client-side rendering.

The server-side approach means the Kindle only needs to load static HTML pages with minimal CSS. There's no JavaScript to parse or execute, no complex layouts to calculate, and no external stylesheet requests to slow down page loads. This matches the Kindle's strengths perfectly.

Data Flow

The data flow is straightforward and efficient. The server fetches items from the Readwise Reader API on demand, with reasonable caching to avoid hammering the API. For article content, the server parses and sanitizes HTML, then paginates it into manageable chunks. Each page render triggers an update to your reading progress via an API call, but this happens asynchronously so it doesn't slow down page loads.

The route structure mirrors common web reading patterns. The root path displays your inbox as a list of available articles. Each item links to a reading view that starts at page one. The reading view shows one page of content at a time, with clear navigation controls to move between pages. An archive endpoint allows you to mark articles as read when you're done.

Pagination Logic

The pagination preprocessor is the heart of the reading experience. It takes sanitized HTML and intelligently splits it into pages. First, it parses the HTML into block-level elements like paragraphs, headings, blockquotes, lists, and images. Then it walks through these blocks, accumulating them into the current page.

For text blocks, the algorithm adds them to the page if the cumulative character count stays under budget. If adding the next block would exceed the budget, it starts a new page. This ensures that entire paragraphs stay together rather than being awkwardly split mid-thought.

For images, the strategy is different. The current page is closed, and the image gets its own dedicated page. This prevents layout issues and ensures images display prominently at a readable size. You could alternatively put the image plus a following paragraph together if you prefer more compact pagination.

The paginated output is stored in memory or cache, keyed by document ID. This means the pagination work only happens once per article, with subsequent page turns simply retrieving the pre-calculated pages from cache.

HTML Output Design

The HTML output is deliberately minimal. The markup uses basic semantic elements with simple inline styles. The body gets a readable serif font, comfortable margins, and appropriate line height. Images are constrained to fit the screen width. Navigation elements are clearly separated from content with adequate spacing.

All CSS is kept inline or in a single style block to avoid external stylesheet requests. This reduces network latency and ensures the page renders immediately without waiting for additional resources to download.

Content Sanitization

Content sanitization is crucial for both security and compatibility. The application uses specialized libraries to strip Readwise Reader HTML down to a safe subset of allowed tags. Only semantic text elements like paragraphs, headings, emphasis, and strong text are preserved. Lists including both ordered and unordered variants are supported. Links and images are allowed but stripped of potentially problematic attributes.

All inline styles are removed to prevent layout-breaking CSS from upstream sources. Scripts are obviously stripped for security. The result is clean, simple HTML that renders consistently on e-ink displays without any surprises.

Caching Strategy

The two-tier caching strategy balances performance and freshness. The item list cache holds your inbox for a few minutes, refreshing on explicit reload or after archiving an item. This keeps the list reasonably current without making you wait for an API call every time you return to the inbox.

Document content and pagination are cached more aggressively. Once an article is loaded and paginated, it stays in cache until you archive it or explicitly invalidate the cache. This makes sense because article content doesn't change, so there's no need to refetch or reprocess it.

For personal use, a simple in-memory dictionary is sufficient for caching. You're not dealing with scale concerns or multiple users, so there's no need for complex cache invalidation strategies or distributed caching systems.

Reading Progress Updates

Reading progress is updated via fire-and-forget async tasks. The application calculates your progress as the current page divided by total pages, then creates an async task to update this progress in Readwise. This means page loads aren't blocked waiting for API updates to complete.

Progress updates happen in the background while you're already reading the page. If an update fails due to network issues, it doesn't affect your reading experience. The next successful page turn will update your progress, so temporary failures don't cause permanent loss of tracking.

Determining Your Page Budget

The page budget is best determined empirically. Create a test route that renders Lorem Ipsum at various character counts: 1000, 1500, 1800, 2000, 2500. Load each test page on your Kindle and note which fits comfortably without requiring scrolling. That's your ideal budget.

Do the same test with pages containing images to decide how to handle image pagination. You might find that an image plus a short caption works well together, or you might prefer images always getting their own dedicated page.

Once you've determined your ideal settings, you can hardcode them in the configuration. There's no need for responsive breakpoints or client-side detection when you're optimizing for a single known device.

API Routes

The API surface is intentionally small and focused. The root GET endpoint lists inbox items, providing a gateway to your reading material. The read endpoint with just a document ID redirects to the first page, making it easy to start reading with a simple link.

The read endpoint with both document ID and page number displays the specific page, handling all the content fetching, sanitization, pagination, and progress tracking. The POST archive endpoint marks documents as read, then redirects back to the inbox.

A health check endpoint provides a simple way to verify the service is running, useful for monitoring or container orchestration systems.

Troubleshooting

The most common issue is forgetting to set the Readwise API token. The config module validates this on startup and will clearly tell you if it's missing. Make sure you've created a .env file with your token from the Readwise website.

If pages are too long or too short on your device, adjust the page character budget in your configuration. Start with the default of 1800 and tune up or down based on what feels comfortable on your specific Kindle model.

Slow page loads on the first view of each article are expected, as the content must be fetched from the Readwise API, sanitized, and paginated. Subsequent page turns use cached data and should be nearly instant.

If images aren't displaying, check that your Kindle has network access and can load external images. Some Kindle models or network configurations may have restrictions on image loading from external domains.

Container Integration

For deployment in a containerized environment, the application integrates cleanly with standard container infrastructure. Add the required dependencies to your existing pip install command: beautifulsoup4 for HTML parsing, bleach for sanitization, and cachetools for the in-memory cache implementation.

The Dockerfile assumes fastapi, uvicorn, httpx, and jinja2 are already installed as part of your base image. These are common dependencies for Python web applications, so they're likely already present in your environment.

Configure supervisord to manage the application process, setting it to autostart and autorestart for reliability. Direct logs to appropriate files for monitoring and debugging. The application runs on an internal port and should be proxied through nginx for external access.

The nginx configuration should include proxy headers to preserve client information and handle the forwarding correctly. The application will be accessible at a clean URL path through the proxy, making it easy to access from your Kindle browser.

Conclusion

This application demonstrates that sometimes the best solution is the simplest one. By targeting a specific device with known constraints, using server-side rendering with minimal client-side complexity, and focusing on the core reading experience, you can create a tool that works reliably and performs well within the Kindle's unique environment.
